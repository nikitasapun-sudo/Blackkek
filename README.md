# Blackjack Omega II v3.13 PWA — учебная лаборатория

Автономная математическая демонстрация finite-shoe вероятностей и условных результатов на **виртуальных учебных очках**. Без денежных ставок и игровых сервисов.

## Запуск и установка
Откройте `index.html` для локальной работы. Для установки PWA разместите файлы на статическом HTTPS-хостинге (например, GitHub Pages). После первой загрузки service worker кэширует интерфейс и дальнейшая работа возможна автономно. GitHub Pages настроен на **GitHub Actions**. Адрес сайта: https://nikitasapun-sudo.github.io/Blackkek/. Публикация выполняется workflow `.github/workflows/publish-pages.yml` при изменениях в `main`.

## Подтвержденные расчёты
- Натуральный A+10 vs A после успешного peek: +1.5 при выплате 3:2.
- DOUBLE 5+6 vs A без peek: -0.5339379694 (`loseAll`) и -0.2240106086 (`originalOnly`).
- Charlie: выключен, шесть или семь карт; DOUBLE: любые две, 9–11 или 10–11.
- SPLIT без повторного разделения. Если точный расчет слишком сложен, программа сообщает о лимите, не выдавая приближение за exact.

Это учебные модельные допущения, не подтвержденные правила конкретного мобильного приложения.
## v3.5: автономное вычисление
Сценарии `Рассчитать все сценарии`, `Удвоить · расчёт` и `SPLIT · расчёт` выполняются **только в виртуальной учебной модели**. Кнопки не играют за пользователя и не обращаются к реальным игровым серверам. Для точного расчёта SPLIT без повторного разделения учитывается общая колода двух рук; в сложных ситуациях временной или ресурсный лимит может завершить вычисление без ответа.

Скрипт `omega_worker.js` и математическое ядро `omega_v34_core.js` сохраняются в PWA-кэше при первой онлайн-загрузке. После обновления установленной PWA нужно один раз запустить её онлайн, затем проверить вычисление в автономном режиме. Новые версии приложения выходят с новым ключом кэша.

Независимые математические тесты включают контрольные примеры на **обеднённой колоде**: обычное сравнение, DOUBLE, SPLIT с одной картой и полный SPLIT тузов с ограничением одной карты. Тесты не доказывают точность всех комбинаций правил. При отказе от сложного расчёта нет замены результата приблизительным числом.

## v3.7: состояние почти пустой колоды
- Если в остатке меньше трёх неизвестных карт, виртуальный SPLIT недоступен, потому что нужны закрытая карта дилера и две карты разделённых рук; доступный STAND остаётся рассчитанным.
- Если рассчитаны обычные варианты, а модель ограниченного SPLIT не может завершить дилера из-за нехватки карт, обычные значения сохраняются, а SPLIT показывает явное пояснение. Недостаток карт не заменяется воображаемым «точным» EV.
- Дополнительный независимый oracle проверяет **полный оптимальный SPLIT** на 24 сценариях информационных состояний с распределением закрытой карты, режимами peek/no-peek, DAS и OBO. Для всех комбинаций карт этот тест не является доказательством.
- GitHub Actions отдельно проверяет автономную загрузку в Chromium после обновления PWA.

## v3.8: ограниченная память полного SPLIT
В прежней версии точный двухрукий SPLIT прекращался, когда кэш распределений дилера достигал 500 000 записей. Теперь четыре кэша (`dealer`, `first`, `second`, `terminal`) ограничены по размеру. При заполнении старые результаты удаляются и могут быть точно вычислены заново: это **не приближение** и не меняет правила. В диагностике доступны `cacheLimits`, `cachePeak` и `cacheEvictions`.

Тяжёлые состояния могут всё ещё закончиться ограничением времени или ресурсов телефона. В этом случае полный SPLIT **не считается рассчитанным**, а уже успешно завершённые основные результаты сохраняются. Дополнительные тесты проверяют, что результат не меняется при искусственно малом размере кэшей.

## v3.9: общий исход дилера при вычислении двух рук
Для каждой конфигурации остатка колоды распределение исходов дилера, усреднённое по допустимым закрытым картам, одинаково для обеих завершённых частей SPLIT. Теперь оно вычисляется один раз и сохраняется в ограниченном кэше `publicDealer`. Это устраняет повторный перебор закрытой карты для одинакового открытого информационного состояния. Две руки по-прежнему используют общий остаток; повторное разделение не включено.

Новый кэш содержит точные значения, которые при вытеснении можно вычислить повторно. Для некоторых сложных сценариев предел времени на мобильном устройстве по-прежнему может быть достигнут. В такой ситуации результат полного SPLIT не публикуется как точный. Контроль включает независимый oracle и проверку неизменности результата при малом кэше.

## v3.10: локальная диагностика сложного SPLIT

При превышении лимита времени приложение **не** заменяет точный результат приближённым. Для воспроизведения сложного состояния доступны кнопки «Показать диагностику» и «Скопировать отчёт». Отчёт формируется локально: версия, исходные карты, открытая карта дилера, число уже известных карт каждого номинала, выбранные учебные правила, продолжительность, этап расчёта, количество состояний и размеры кэшей. Он не содержит личных данных и никуда автоматически не передаётся.

Встроенный Worker передаёт промежуточную статистику с ограниченной частотой; при внутреннем тайм-ауте экспортируется последняя диагностика прямо из математического ядра. Это помогает различить перегруженную рекурсию дилера и перебор вариантов двух рук. Лимиты памяти и времени не повышались, правила и точные вероятности не изменены. Реальное воспроизведение пользовательского SPLIT возможно только после получения такого отчёта.

## v3.11: сжатие точных состояний SPLIT
В математических вариантах без Charlie после разделения и без удвоения после разделения длина каждой дочерней руки не влияет на дальнейшие решения и итог. v3.11 исключает её из ключей кэширования точно эквивалентных состояний. При включённых правилах, которым длина нужна, она сохраняется. Это оптимизация идентичных математических состояний, а не приближение и не обещание решения всех случаев за 22 секунды. В тестах также воспроизводится присланная пользователем раздача 7–7 против 5 с 389 неизвестными картами и проверяется диагностика тайм-аута.

## v3.12: ускорение полной рекурсии дилера
Приложение повторяет диагностический сценарий 7–7 против 5 при 389 неизвестных картах и режиме `originalOnly`. Для сокращения накладных вычислений состояние колоды в кэше дилера кодируется точным целым числом смешанного основания; при доборе карты ключ изменяется арифметически. Все значения уникальны в пределах исходных восьми колод и не выходят за безопасные целые JavaScript. Действия и вероятности не меняются.

Переходы между очками дилера и терминальные распределения теперь создаются один раз на расчёт. Точность проверяется независимыми контрольными примерами SPLIT и ограниченным кэшем. Даже при оптимизации полный SPLIT с большим остатком колоды может не завершаться за 22 секунды на Android; такое состояние не выдаётся за точный результат.

## v3.13: точный ограниченный SPLIT при нехватке времени
При расчёте SPLIT кнопка сначала вычисляет отдельное **точное ограниченное** значение: одна дополнительная карта каждой из двух разделённых рук, затем остановка обеих. Это именно `splitTwoCardStop`, а не оптимальный полный SPLIT. После него продолжает вычисляться полный SPLIT с возможностью дальнейших решений. Если полный расчёт превысит лимит времени, ограниченный результат остаётся на экране с явным пояснением, а поле полного SPLIT не выдаёт никакого числа. При успешном завершении показаны оба разных учебных сценария. Никаких приближённых результатов или денежных ставок нет.

## Независимый математический аудит (Julius / Python)

Независимая Python-реализация с `fractions.Fraction` вычисляет точные вероятности конечной колоды, закрытой карты дилера, его розыгрыша и оптимального продолжения доборов. Результаты не берутся из JavaScript-движка: его значения сравниваются с отдельно полученными рациональными эталонами. Фикстуры проверяются автоматически:

- `tests/julius_rational_oracle.cjs`: **80 сравнений STAND/DOUBLE** на 40 состояниях из аудита №14.
- `tests/julius_hit_charlie_oracle.cjs`: **408 сравнений STAND/HIT** на 204 состояниях, включая S17/H17, мягкие и жёсткие суммы, дилерский peek, Charlie на 6 и 7 картах и отключённый Charlie.
- `tests/julius_boundary_oracle.cjs`: **23 проверки** на 13 малых остатках колоды, включая Charlie, natural, surrender и отсутствие публичных карт для добора.

Область проверки ограничена перечисленными правилами и входами. Эти тесты не доказывают безошибочность всех состояний восьми колод и не разрешают сложный полный SPLIT. Числа относятся только к автономной учебной математической модели.

## Аудит условных вероятностей последовательных карт (Julius, этап 3)

- `tests/julius_sequential_hole_oracle.cjs`: **154 конечные колоды из 12–16 неизвестных карт**, **308 сравнений STAND/HIT** с независимой Python-реализацией. Эталон моделирует сначала **конкретную скрытую карту дилера**, затем вероятности каждой последовательности открытых карт с учётом этой скрытой карты, обновляет апостериорные вероятности по Байесу и решает оптимальное продолжение рекурсивно на точных рациональных числах. Это другой путь вычисления, чем публичная композиция карт в JavaScript.
- `tests/julius_sequential_posterior.cjs`: **8 трёхкарточных последовательностей** с различными peek и открытыми картами A/10/5. Проверяются **168 точных апостериорных и последовательных вероятностей**, полученных независимым перебором всех допустимых скрытых карт.
- Оба набора проверяются при изменениях в `main` и перед публикацией PWA.
- Нет изменений в игровом ядре, SPLIT, пользовательских правилах, лимитах времени и офлайн-PWA. Результат охватывает конкретные контрольные колоды, а не все состояния исходных 416 карт.

## Независимый аудит численной устойчивости полного башмака (Julius / Python)

На восьми колодах (416 карт до удаления видимых) использованы отдельные высокоточные расчёты `decimal.Decimal` с точностью 46–48 значащих цифр и рациональные значения `fractions.Fraction`. Эталон сначала перечисляет возможную закрытую карту, затем завершение дилера и условный добор игрока. В приложении проверяется результат `OmegaFiniteEV.solve` без полного SPLIT.

- `tests/julius_full_shoe_decimal.cjs`: **22 STAND** и **16 DOUBLE** независимо вычисленных ожиданий, а также **22 проверки** нормализации высокоточного распределения дилера. Остатки: 413, 407, 386, 347, 284 и 197 неизвестных карт; S17/H17, peek/no-peek, обе модели расчёта dealer BJ.
- `tests/julius_full_shoe_bayes.cjs`: **24 последовательности** наблюдений на остатках 413, 389, 287, 197; **504 точных рациональных** сравнения условного распределения скрытой карты, следующего публичного добора и вероятности последовательности. Дополнительно проверяются суммы распределений и соответствие состава колоды производственной `inputCounts`.
- `tests/full_shoe_numerical_invariants.cjs`: порядок введения раскрытых карт не должен менять результаты STAND/HIT/DOUBLE; проверяются граничные пределы EV и отсутствие NaN/Infinity при различных уровнях удаления карт.

Численные допуски учитывают конечную точность JavaScript Number, не подменяя вероятности симуляцией или приближённым SPLIT. Аудит обнаруживает регрессии в проверенных состояниях, но не является доказательством корректности всех (416!) порядков или математической сертификацией любого пользовательского сценария.

## v3.14: соответствие интерфейса учебной математической модели

- Раздел «Следующая случайная карта» показывает вероятности **следующей публичной карты с неизвестной скрытой картой дилера**, а при `Peek: дилер проверил` и открытой A/10 учитывает **условие успешной проверки (нет натурального блэкджека дилера)**. Ранее этот раздел показывал простые частоты по неизвестному остатку без условия peek, хотя finite-shoe EV это условие учитывал. Указано условие непосредственно возле таблицы. При единственной неизвестной карте (резервированной скрытой дилером) публичный добор не показывается.
- Выбранные значения настройки учебных правил (peek, S17/H17, Charlie, double, выплаты, тайминг сдачи и другие настройки EV) теперь сохраняются в локальном браузере и восстанавливаются при повторном запуске. Восстанавливаются только допустимые значения из явных белых списков; карты и правила хранятся отдельно. Никакая информация не отправляется на сервер.
- При изменении учебных правил работающий автономный расчёт отменяется, отображаемые EV очищаются, следующий расчёт использует обновлённые правила. Проверено автоматическими тестами и в Chromium без интернета.
- Это исключительно исправление интерфейса, не изменение математических формул, payout, конечной колоды или временных ограничений.


## v3.15: обновление офлайн-PWA и сохранение состояния

Service Worker хранит статические файлы и вычислительный модуль в одном кэше текущего выпуска `omega-ii-v315-1`. При переходе на новую версию он удаляет только устаревшие кэши Omega II, не затрагивая `localStorage` карт и правил. Устаревшие файлы других выпусков больше не подмешиваются через глобальный поиск `caches.match`.

Навигации по `/` и `/index.html` с параметрами адреса (например, `?update=315`) при отсутствии сети открывают сохранённую стартовую страницу. Этот fallback ограничен только стартовыми адресами текущего PWA, а не всеми несуществующими URL.

Если новая версия Service Worker получает управление **уже открытой** вкладкой, старые отображаемые EV очищаются, незавершённый Worker прекращается, а приложение предлагает нажать **«Открыть новую версию»**. Автоматического перезапуска посреди редактирования карт нет. Карты и выбранные правила сохраняются как прежде. При первой установке PWA уведомление не требуется.

`tests/browser_upgrade.cjs` проводит реальное обновление Service Worker в Chromium: тестовый прошлый выпуск → новый, офлайн-закрытие и открытие, переход по адресу с `?update`, очистку старого кэша, сохранение карточного состояния и правил, отключение старого результата, а также новый автономный расчёт без интернета. Это имитация жизненного цикла Chromium, а не утверждение о тестировании непосредственно на физическом Android.


## v3.16: проверка сохранённых данных

При восстановлении проверяются все четыре списка карт, допустимые ранги, предел 32 карт каждого ранга и ограничения длины рук. Повреждённая или неполная карточная запись не перезаписывается: ввод и расчёт блокируются до подтверждённой «Тасовки». Валидные карты сохраняются при восстановлении некорректных настроек интерфейса; неизвестные поля не импортируются. Некорректные правила заменяются стандартными с уведомлением.

Сбой чтения или записи localStorage показывается в отдельном доступном статусе. При сбое записи работа продолжается в памяти вкладки; следующая успешная запись соответствующего ключа снимает сообщение. Успешное сохранение карт не скрывает ошибку сохранения правил. Математическое ядро не менялось. Проверки включают повреждённые данные, отказы хранилища и восстановление в офлайн Chromium.


## v3.17: конфликт между вкладками

Изменение или удаление сохранённых карт/правил в другой вкладке останавливает Worker, очищает EV и диагностику и блокирует запись из устаревшей вкладки. Кнопка «Загрузить сохранённые данные» вручную перезагружает страницу, заменяя локальные изменения сохранёнными. События storage, возврат к вкладке, запуск расчёта и сохранение проверяют оба ключа. Очередь сообщений старого Worker не восстанавливает устаревший EV.

В браузере с Web Locks сравнение и запись выполняются под общей блокировкой omega-mini-storage. Одновременные записи двух вкладок этой версии не перезаписывают победившую запись. Старые версии приложения не используют эту блокировку: обновите все вкладки. В браузере без Web Locks остаётся проверка перед записью, но строгой защиты от одновременных записей нет; интерфейс предупреждает использовать одну вкладку. Проверка в двух офлайн-вкладках Chromium входит в CI. Математическое ядро не изменено.

## v3.18: учебная рамка для решения о ставке

Добавлен отдельный раздел с условиями, при которых виртуальную ставку можно рассматривать: состав карт и правила должны быть введены точно, расчёт должен завершиться, а EV должен быть выше нуля. Там же перечислены причины пропустить раздачу: отрицательный или неизвестный EV, несовпадение правил, повреждённое состояние, конфликт вкладок, достигнутый личный лимит, усталость или попытка отыграться.

Раздел объясняет долгосрочный смысл положительного EV и не выбирает реальную ставку, размер ставки или момент игры. Математическое ядро не менялось.

## v3.19: стратегия по составу и виртуальный edge

Добавлены три учебных слоя. Сравнение стратегии считает конкретную руку на текущем составе остатка и сопоставляет оптимальное действие с baseline свежего восьмиколодного башмака при тех же S17/H17, peek, surrender и Charlie. В интерфейсе сначала выбирается собственный ответ, затем показываются правильное действие, разница EV и True Count.

Отдельный aggregate edge усредняет оптимальное одиночное решение по всем двум картам игрока и открытой карте дилера из текущего остатка. Он учитывает момент до peek, число оставшихся карт и фактическое проникновение; полный SPLIT исключён и рассчитывается отдельно. Порог не задаётся одним True Count: приложение показывает edge текущей модели и явно сообщает, если точный расчёт не завершён.

Математическое ядро не выдаёт размер ставки и не подключается к денежным игровым сервисам.

## v3.20: свободный тренажёр стратегии

Тренажёр получил случайные задачи по hard, soft и pair рукам. Подсказка с оптимальным действием, EV, True Count и отклонением от baseline показывается сразу после выбора задачи; ответ вводить необязательно. Добровольные попытки считаются отдельно: сохраняются число попыток, точность и среднее отставание EV на этом устройстве.

## v3.21: рекомендация по виртуальным фишкам

Добавлена отдельная учебная рекомендация по бесплатным виртуальным фишкам. При неизвестном или неположительном aggregate edge приложение рекомендует 0 фишек; при положительном edge — 1 фишку; при edge от 1% и виртуальном банке от 100 фишек — не более 2. Это фиксированная схема без увеличения после проигрыша и не расчёт реальной ставки.

## v3.22: компактный интерфейс

Уменьшены отступы и высота основных элементов на телефоне, настройки EV собраны плотнее, а расширенные учебные блоки свернуты по умолчанию. Изменения касаются только представления и не меняют встроенное математическое ядро, Worker, входные данные или точность расчётов.

## v3.23: сравнение виртуальных ставок x1 и x2

После точного aggregate edge тренажёр показывает EV для x1 и x2. Значение x2 получается линейным умножением того же edge на две условные единицы; это не отдельная вероятностная модель. Рекомендация x2 появляется только при edge от 1% и виртуальном банке от 100 фишек.
